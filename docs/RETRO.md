## 2026-11-13 (2 回目。v0.5.1〜v0.7.0 のセッションの後)

### 持ち主が気になったこと
- 実装以外の進捗が微妙。視野が狭い (**繰り返し**: 1 回目 (#41) でも「外も調べて視野を広げる」を足していた)
- 1 つの PR に何度も push し、CI を自分で取り消し続けたのは賢くない。待つ間は実装以外をすればよい
- 不具合の修正の PR (#47) に機能の追加まで入った。PR は Issue に沿って作り、別の作業は Issue にしてから対応する方が分かりやすい
- e2e の失敗の原因の特定に約 1 時間。最速なら仕方ないが、改善できるならする
- 良かったこと: リリースの頻度 (1 回で 3 つ) と報告の読みやすさは、前より良い
- 使用量の上限で止まるのは想定内 (使い切るつもりで走らせている)。こちらでどうにかすることではない

### Claude から見えたこと
- 仕事を「PR になるか」で数えていて、調べたことが形に残らず、すぐ実装に戻っていた
- やることの出発点がコードと Issue で、使う人や外の世界からではなかった
- e2e の失敗は「main でも起きるか」と「記録を足す」を最初にしていれば、CI 1〜2 回分縮められた
- マージ後に作業ブランチを作り直したため、上書きの push が要る状態にしていた (main を取り込めば普通に push できた)

### 決めた直し方
- 調べたことを docs/RESEARCH.md に残し、実装と同じ成果物として扱う。調べる対象を一覧にせず、当たり前を疑うところから入る。どこから入ったかを書く
- PR の目的は 1 つ。途中で見つけた作業は Issue にする
- 失敗の原因は、推測で直す前に手がかりを増やして確かめる
- 持ち主が気になったことは、このファイルに残す
- (CLAUDE.md に入れなかったもの) 「CI の実行中は push しない」は、待ち時間に調べものをすれば起きないので入れない。「マージ後は main を取り込む」は手順なので ROADMAP に置く
