# UI の原則と、画面の点検 (D-045)

Web 版・Flutter 版をなぞる前提を捨て、チャットクライアントの UI を 0 から考え直すための調査と方針。
2026-11-13 に調べた。判断は D-045 (docs/DECISIONS.md) に要約がある。

## 0. この文書の前提 (持ち主との相談で決めたこと)

- 判断の材料は「世の中の情報」(研究・公式の指針・他社アプリの作り・ストアレビュー)。原則には出典を付ける。
- 持ち主の感覚・実機での操作は確認の材料にしない (D-024)。
- 今の配置を守ることに価値を置かない。見た目が大きく変わってよい。
- Google の M3 Expressive の調査は根拠にしない。Material の指針は参考の一つで、正しさの根拠にはしない
  (この文書で使う Android の公式文書は、数値の基準 (48dp・16ms・700ms・起動の秒数) だけ)。
- 待ち時間は、見せ方の工夫 (スケルトン・回転アイコン) より、キャッシュをすぐ出して「待たせない」ことを選ぶ。
- 実機での滑らかさの絶対値は測れないものとして進める。

## 1. チャットクライアントの役割

利用者がチャットアプリでしていること (出典から):

| 役割 | 出典 | Giracle での具体的な操作 |
| --- | --- | --- |
| 新しい発言にすぐ気づき、読む | WhatsApp が SMS より使われる理由の一つが「すぐ届く (immediacy)」(Church & de Oliveira 2013, MobileHCI。要約) | 通知・ホームの未読から開く。開いたら未読の始まりが見える |
| 短く返す・反応する | 職場の IM は、短い質問・調整・「今話せるか」の確認に使われる (Nardi ほか 2000, CSCW。要約) | 返信・リアクション・入力 |
| 自分宛てを拾う | Slack は「Activity」を目立つ場所に出し「Mentions and reactions」に改名した (Slack 2020 年の公式ブログ。要約) | 受信箱 (メンション・返信) |
| 会話を切り替える | Slack は 2020 年に、届きにくかった DM の一覧を下のタブに出した (同上)。Discord は 2023 年の刷新で、サーバーと DM を別のタブに戻した (Discord 公式ブログ。要約) | チャンネル間の移動 |
| 探す | Discord は刷新への声を受けて、DM 全体の検索を足した (同上) | 検索 |
| つながっていない間も使える | 低評価レビューの多くが「Connecting…のまま読めない・送れない」(4 章) | キャッシュの表示・送信待ち (D-029) |

ここから、**読む・返す・自分宛てを拾う・切り替える・探す** を「よく使う操作」として扱う。
設定・メンバー一覧・チャンネル一覧 (参加していないもの)・サーバー管理は「たまに使う操作」として扱う
(頻度を測ったデータは無い。上の出典からの判断)。

## 2. 機械的に確かめられる基準

| 基準 | 値 | 出典 |
| --- | --- | --- |
| 応答の目安 | 0.1 秒: 直接操作している感覚が保たれる。1 秒: 考えの流れが途切れない。10 秒: 注意が保たれる限界 | Nielsen 1993 (Miller 1968・Card ほか 1991 に基づく。要約)。「Miller が 0.1/1/10 を言った」という引き方は誤りとする指摘もある (要約) |
| 押せる範囲 | 48dp × 48dp 以上 | Android 公式「Make apps more accessible」(本文を確かめた) |
| 片手の親指で押せる大きさ | 単発の操作 9.2mm、続けて押す操作 9.6mm | Parhi, Karlson, Bederson 2006, MobileHCI (要約)。48dp ≒ 7.6mm (160dpi 基準) |
| 指の精度は位置で変わる | 画面の中央 7mm、端 9mm、隅 12mm | Hoober 2017 (UXmatters「Design for Fingers, Touch, and People」・講演の再掲。要約) |
| 持ち方 | 片手 49%・片手で持ち他方で操作 36%・両手 15% (1,333 件の観察、2013) | Hoober 2013 (UXmatters。要約)。Hoober 自身が 2017 年に、古い前提の上の結論だったと書き直している (要約)。「親指の届く範囲」の緑・黄・赤の図は誤りだとも述べている (要約) |
| 下限 (参考) | WCAG 2.2 の 2.5.8 (AA) は 24 CSS px、2.5.5 (AAA) は 44 CSS px、Apple は 44pt | W3C・Apple (要約)。Android の 48dp より緩いので、このアプリでは 48dp を使う |
| 文字の濃さの差 | 18sp 未満 (太字は 14sp 未満) で 4.5:1、それ以外 3:1 | Android 公式 (本文を確かめた) |
| フレーム | 60fps で 16ms 以内。700ms を超えると「固まった」フレーム | Android 公式「Slow rendering」(本文を確かめた) |
| 起動 | コールド 5 秒・ウォーム 2 秒・ホット 1.5 秒以上を Android vitals が「長すぎる」とする | Android 公式「App startup time」(本文を確かめた) |
| 待ち時間の見せ方 | 136 人の比較で、体感の待ち時間はスケルトン 2.82 秒 > 回転アイコン 2.41 秒 > 空白 2.29 秒。「速く読み込まれた」と答えた割合はスケルトン 59%・回転 74%・空白 66% | Viget 2017「A Bone to Pick with Skeleton Screens」(要約。原文の表は開けていない)。逆の結果を言う記事もあり、標本が小さい |

Hoober の指摘から、「親指の届く範囲の図」で上下を切るのではなく、**隅を避け、よく使う操作を中央寄り・下寄りに置く** と読む。
持ち方は人と場面で変わるので、左右どちらかに寄せることはしない。

## 3. 他社アプリの作り

### Element X Android (コードで確かめた)

- ホーム: 上に検索とアカウント、その下に絞り込みのチップ (未読・人・部屋・お気に入り・招待)。
  下に浮いた小さな道具 (「チャット」「スペース」の切り替えと、新しい会話のボタンを中央に) を置く
  (`HomeView.kt` の `HomeBottomBar`・`FabPosition.Center`)。今の項目をもう一度押すと一覧の先頭へ戻る。
- 一覧の行の長押しで、既読にする・お気に入りなどのメニュー (`RoomListContextMenu.kt`)。
- 会話: 新しいものが下 (`reverseLayout = true`)。「最新へ」と「未読の始まりへ」のボタンを別に持つ (`TimelineView.kt` の `JumpToUnreadState`)。
  スクロール中は日付を浮かせて出す (`FloatingDateBadge`)。右へすべらせて返信 (`ReplySwipeIndicator`)。
- メッセージの長押しで下からメニュー。先頭に最近使った絵文字の列 (`ActionListView.kt` の `EmojiReactionsRow`)。

### Signal Android (コードで確かめた)

- 新しい会話とカメラの丸いボタンを右下に置く (`MainFloatingActionButtons.kt`)。
- 未読だけに絞る操作がある (`MainToolbar.kt` の `onFilterUnreadChatsClick`)。

### Slack (公式ブログの要約)

- 2020 年のスマホ版の刷新: DM の一覧が届きにくかった (iPhone は知られていない横すべり、Android は選択の一覧) ので、下のタブに出した。
  「Activity」を目立つ場所に出し、「Mentions and reactions」に改名した。
- 2023 年の刷新はデスクトップ版 (Home・DMs・Activity)。発表の数時間で批判が出た。製品デザインの責任者は「Slack は通知の量と、情報の置き場所の多さで圧倒されると感じられる、という声が最も多かった」と説明した (VentureBeat。要約)。

### Discord (公式ブログ・報道・サポートの掲示板の要約)

- 2023-12 の刷新に強い反発。掲示板の声は「サーバーと DM の行き来に 2〜3 秒かかる」「前より遅い」「操作がもたつく」。
  元に戻さないと明言した (要約)。
- 公式ブログでは、試験中の声を受けて作り直し、サーバーと DM を別のタブに戻し、サーバーの縦の帯を残し、DM の先頭固定・DM 全体の検索を足したとする。
  アプリを開く時間は iOS で 43%・Android で 55% 短くなったとする (要約)。2024-04 のパッチノートでサーバーの切り替えが 30% 以上速くなったとする (要約)。
- 教訓 (持ち主との相談どおり): 反発の中身は「配置を変えたこと」より **遅さ** と **よく使う操作が遠くなったこと**。

### Telegram Android (報道・要望掲示板の要約)

- 2026-02 の 12.4.0 で、横から出るメニューを、常に出る下の 4 つのタブに替えた。反応は否定的。
  主な声は「チャットの一覧の場所が減った」「時間のほとんどはチャットのタブにいる (他のタブは場所の無駄)」「隠す設定が欲しい」(9to5Google・掲示板。要約)。
- 教訓: **行き先が少なく、ほとんど 1 か所にいるアプリでは、常に出る帯は場所を取るだけ**。Slack の 2020 年 (行き先が多く、届きにくかったものを出した) とは条件が違う。

## 4. ストアレビューの傾向

公開データ 2 つの低評価 (星 1〜2) を見た。手順とデータの場所は `docs/ui-research/review_keywords.py` の先頭にある。

- Telegram (Google Play、10,000 件、2021-09〜2022-03): 低評価 5,043 件
- WhatsApp (3,927 件、取得時期の記載なし): 低評価 1,109 件

| 接続・送受信 (「Connecting…」のまま・届かない) | 26 | 0 |
| 不具合・落ちる | 13 | 14 |

| データ消失 (履歴・バックアップ) | 0 | 5 |
| 通話 | 5 | 1 |

キーワードでの粗い分類 (全件。英語の決まった言い回しにしか当たらない) でも、「操作・配置」に当たるのは Telegram 3.1%・WhatsApp 1.8% で、
同じく「接続・送受信」は Telegram 27.8%、「遅い」は Telegram 10.4%・WhatsApp 4.6% だった。

**読み方と限り**

- 低評価の大半は「使えない」(つながらない・落ちる・取れない) で、画面の配置への不満は少ない。
  ただしこれは配置が重要でないことを意味しない (配置に不満があっても、星 1〜2 を付けるほどでないことが多い、とも読める)。
- 「Connecting…」の不満の多くは「その間、読めない・何もできない」こと。
  → 接続を待たずに、手元にあるものを読める・書けること (原則 P-2) の根拠にする。
- データの時期が偏る (Telegram は 2021〜2022 年。Android 11 の保存領域の変更の頃で「保存先が見えない」が多い)。
  分類は 1 人 (Claude) で、別の人との一致は測っていない。標本は 160 件と小さい。Discord・Slack・Signal のレビューは手に入らなかった
  (Play ストアに届かず、GitHub に公開データが見つからなかった)。

## 5. 原則

各原則に、確かめる方法 (8 章) を付ける。数字は 2 章の出典から決めた。

- **P-1 待たせない**: 一度見たもの (チャンネルの一覧・メッセージ・画像) は、通信を待たずにすぐ出し、新しいものは裏で取って差し替える。
  画面の中央に回転アイコンを出すのは、手元に何も無いときだけ。スケルトンは使わない。
  根拠: Nielsen の 1 秒、Viget 2017、Discord の刷新への反発 (遅さ)、レビューの「Connecting…」。
- **P-2 つながっていなくても読める・書ける**: 接続の状態は小さく正直に出すが、それで読む・書くを止めない (送信は D-029 の送信待ちへ)。
  根拠: レビューの「接続・送受信」(Telegram の低評価の約 4 分の 1)。
- **P-3 よく使う操作は近くに**: 読む・返す・自分宛てを拾う・切り替える・探すは、ホームかチャンネルから 2 手以内。
  画面の上の隅には、よく使う操作を置かない (隅の精度 12mm は中央 7mm より大きくずれる)。
  根拠: Hoober 2017、Slack 2020、Discord 2023。
- **P-4 押せるものは 48dp 以上**: 見た目が小さくても、押せる範囲は 48dp を確保する。
  Compose は見た目が小さい押せる要素の押せる範囲を 48dp まで自動で広げる (`TouchHitBehaviorTest` で、見た目の外を押して確かめた)。
  押せる親の中でも広がるが、すぐ横や真下に別の押せる要素があると、そちらが取り、実際に押せる範囲は 48dp に足りなくなる。並べるときは間を空けるか、見た目から 48dp にする。
  根拠: Android 公式、Parhi 2006 (9.2mm)。
- **P-5 一覧の場所を奪わない**: 常に出る帯 (下のタブ・案内の行) は、行き先が 3 つ以上あって行き来が多いときだけ置く。
  いつも見る必要のない行き先は、まとめて 1 つの入口にする。
  根拠: Telegram 2026 の反発、Slack 2020 (行き先が多い場合)。
- **P-6 配置を変えたら、手数と時間で比べる**: 見た目の変更は止めないが、よく使う操作の手数が増えたり、表示までの時間が延びたりしたら直す。
  根拠: Discord 2023 の教訓。CI で手数と時間を測る (8 章)。
- **P-7 判断の材料を一覧に出す**: どのチャンネルから読むかを、開かずに決められるようにする (最後の発言・時刻・自分宛ての数)。
  根拠: 比べた全アプリ (Element X・Signal・Slack・Discord・Telegram) の一覧が、最後の発言と時刻を出している
  (Element X・Signal はコードで確かめた。他は一般に知られた画面からの判断で、出典は付けていない)。

## 7. 作り直す案

見た目は大きく変わる。順番は決めず、1 つずつ PR にして、8 章の確かめ方を先に入れてから変える。

### ホーム

1. **チャンネルを一番上から**: 5 行の入口 (H-1) を外す。行き先は次の 2 つにまとめる。
   - 「自分宛て N 件」の行: 受信箱に 1 件以上あるときだけ、一覧の上に出す (P-3・P-5)。
   - 「その他」: チャンネル一覧・メンバー (オンラインの人数も) ・サーバー管理・設定を 1 つのシートにまとめる (P-5)。
2. **行に判断の材料を出す** (H-2・P-7): 2 段にし、1 段目に名前と時刻、2 段目に「送信者: 最後の発言」を 1 行。自分宛てがあれば数のバッジ。
   取り方は選択肢がある:
   - A. アプリだけで作る: 起動時のキャッシュ・WebSocket で届いた発言・開いたときの履歴から、最後の発言を覚えておく。
     サーバーの変更は要らないが、開いたことのないチャンネルは、空のまま (または 1 件だけ取りに行く。チャンネルの数だけ問い合わせが増える)。
   - B. サーバーに、チャンネルごとの最後の発言を返してもらう (サーバー側の変更。docs/SERVER_CHANGES.md に S-9 として相談する)。
   A で始め、問い合わせの数が問題になったら B を相談する。
3. **未読の絞り込み**: 一覧の上に「未読」のチップ (Element X・Signal と同じ)。並びは利用者の並べ替え (D-044) を保つ。
4. **よく使う操作を下へ** (H-3・P-3): 下端の中央寄りに、小さな浮いた道具 (検索・自分宛て・その他) を置く (Element X の作りに近い)。
   常に出る帯は一覧の場所を取る (P-5、Telegram の例) ので、スクロールで下へ読み進める間は隠し、上へ戻すと出す。
   すべて既読は「その他」か、未読のチップの横へ移す (頻度が低く、押し間違えると戻せない)。
5. **つまみの反応する範囲を 48dp に** (H-4。検査には映らないので、検査を待たずに直す)。

### チャンネル

1. **履歴を捨てない** (C-2・P-1): 再接続のときは、開いていないチャンネルの履歴も「キャッシュから」の印を付けて残す (開いているチャンネルと同じ扱い)。
   開いたときにすぐ出し、裏で取り直す。メモリの上限は、チャンネルごとの件数で抑える (今の起動時の復元と同じ考え)。
2. **上端の操作を減らす** (C-1): ミュートはチャンネル情報の画面へ移す。上端は検索と情報だけ。
3. **未読の始まりへ戻る** (C-5): 「最新へ」の上に、未読の始まりへのボタンを、未読の始まりが画面の外にあるときだけ出す (Element X と同じ)。
4. **押せる範囲を 48dp に** (C-4): 絵文字を選ぶ画面の枠。 48dp にすると 1 行に入る数が減る
   (幅 400dp なら概算で 9 個 → 8 個) ので、選ぶ画面は検索で探す使い方と合わせて考える。

### やらないこと (いまの判断)

- 下に常に出るタブ: 行き先がホームと自分宛ての 2 つしかなく、Telegram の反発の条件に当たる (P-5)。DM ができたら考え直す。
- スケルトン: P-1。
- 画面の切り替えの動きを凝ること: 速さが先 (P-6)。

## 9. よく使う作業と、その手数・時間 (D-046)

1 章の「よく使う操作」を、始まりと終わりの状態がはっきりした作業にした。e2e の `uxTasks` (配布版を外から操作する) が、
この順に作業して、手数と時間を CI のログ (「よく使う作業の手数と時間 (ux)」) に出す。
手数は利用者の操作 (押す・長押し・すべらせる・戻る) の回数で、文字の入力は数えない。時間は最後の操作から終わりの状態が出るまで。
エミュレータの時間は絶対値ではなく、前の実行・直す前との比較だけに使う。

準備: チャンネル A に、既読 25 件の後に未読 20 件。チャンネル B に 10 件 (1 件目に検索する語)。どちらも相手 (bob) の投稿。

| 作業 (ログの名前) | 始まり | 操作 | 終わり (測る要素) |
| --- | --- | --- | --- |
| 読む (`read_unread`) | ホーム | A の行を押す | A の未読の始まり (未読 1 件目) が見える |
| 返す (`reply`) | A を開いた直後 | 未読の始まりを右へすべらせる → 入力欄を押す → (入力) → 送信 | 送った返信が画面に見える |
| 切り替える・初めて (`switch_first`) | A | 戻る → B の行を押す | B の最新が見える |
| 切り替える・2 回目 (`switch_again`) | B | 戻る → A の行を押す | A の最新 (自分の返信) が見える |
| 切り替える・つなぎ直した後 (`switch_after_reconnect`) | A (背面に回して戻り、つなぎ直した後) | 戻る → B の行を押す | B の最新が見える (C-2) |
| 自分宛てを拾う (`inbox`) | ホーム (B にいる間に A でメンションされた) | 通知を押す → そのメンションを押す | A のそのメッセージが見える |
| 探す (`search_results` / `search`) | ホーム | 検索を押す → 入力欄を押す → (入力) → 検索を押す / → 結果を押す | 結果の行が見える / B のそのメッセージが見える |

起動の時間は Macrobenchmark の `StartupBenchmark` で別に測っている。

### 基準 (直す前の値)

2026-11-13 の PR #55 の CI (e2e、`7f493c6`)。サーバーはランナーの中 (端末から `adb reverse` の localhost) なので、通信はほぼ待たない。

| 作業 | 手数 | API 35 (ms) | API 37 (ms) |
| --- | --- | --- | --- |
| read_unread | 1 | 745 | 722 |
| reply | 3 | 見えない (8 秒待っても画面に出ない) | 317 |
| switch_first | 2 | 185 | 225 |
| switch_again | 2 | 200 | 276 |
| switch_after_reconnect | 2 | 183 | 185 |
| inbox | 2 | 198 | 243 |
| search_results | 3 | 394 | 182 |
| search | 4 | 361 | 314 |

読み方 (確かめたことと推測を分ける):
- 確かめたこと: 手数は 1 章の「2 手以内」(P-3) を、読む・切り替える・自分宛てで満たす。返す (3 手。入力欄を押す 1 手を含む) と探す (結果まで 3 手、開くまで 4 手) は超える。
- 確かめたこと: API 35 では、読んでいる途中で返した返信が画面に出ない (一覧は最下部にいるときだけ追従する)。API 37 では出た。
  推測: 画面の高さの違いで、API 37 では返信の行が画面の中に入った。
- 確かめたこと: 切り替えは、初めて開く・2 回目・つなぎ直した後のどれも 0.2 秒前後で、差が無い。
  推測: 通信がほぼ待たないので、画面の切り替えの時間が大半を占める。このままでは、キャッシュをすぐ出す直し (C-2 など) の効果が数値に出ない。
  遅い回線を作って測る必要がある (次の作業)。
