### 自分の送信で一番下へ送るのを、嫌がる人はいないか
- 入り口: D-051 で「自分が送ったら一番下へ」を当たり前として直した。逆の意見が無いかを疑った
- 確かめたこと (検索結果の見出しと要約まで。原文は開いていない): 「送ると一番下へ飛んで、読んでいた位置を失う」という不満は、
  主に AI のチャット (Cursor・VS Code の拡張など) で出ている。そこでは長い答えが流れ込むのを読みながら、上の方も読み返すため
  - 2026-11-14 に原文で確かめた (#69): Cursor のフォーラムの要望 (https://forum.cursor.com/t/165924、2026-07) は
    「スレッドを開き直すと一番下へ送られ、長い答えの終わりに着くので、始まりを探して戻る必要がある」。困っているのは長い答えの始まりを探すことで、上の推測と合う
- 確かめたこと: MUI の Chat の説明 (mui.com) は、この環境から開けなかった (ネットワークの設定)。検索の要約では「自分の送信では常に送り、他は下から離れていれば止める」
  - 2026-11-14 に原文で確かめた (#69): 「Messages」(https://mui.com/x/react-chat/basics/messages/) は「利用者が新しいメッセージを送ったとき、
    相手の新しいメッセージが届いたとき、流し込みの間に、一覧は自動で一番下へ送る」。「Performance」のページは「新しいメッセージが届いたら、
    すでに下の近くにいれば一番下へ送る。上へ戻ったら一番下へのボタンを出す」。下からの距離の既定は 150px。
    自分の送信は条件を付けずに書かれているが、「位置に関係なく必ず」とまでは書いていない。要約は大筋で合っていた
- 推測: 人どうしのチャットで送るのは短い文で、送れたかを見たい。AI のチャットとは、送った後に見たいものが違う。
  ただ「返信を書く間、元のメッセージを見ていたい」はあり得る。送った後に元の位置へ戻す手段 (返信の引用を押すと元へ飛ぶ) はもうある

### 人が使うアプリにとって、1.0 は何を意味するか (D-061)
- 入り口: 1.0.0 の目標を持ち主と相談した。最初は「1.0 = 互換を約束する」を当たり前にしていたが、根拠の SemVer・Pantheon・Typst は
  どれも他のプログラムが頼る部品 (公開 API・ライブラリ・言語) の話で、人が使うアプリに当てはまるかを確かめていなかった (持ち主に疑うよう言われて気づいた)
- 確かめたこと (原文、2026-11-14):
  - SemVer の FAQ: 本番で使われている・頼られている API がある・後方互換を気にしているなら 1.0.0 にすべき。Pantheon: stable は finished ではない (どちらもライブラリ向け)
  - Runway: 自動更新のため「多くの利用者にとって版番号は見えないものになった」。Photoroom: 版番号はサポート・古い版を断る仕組みなど作る側のために使う。
    どちらもストアの自動更新が前提。このアプリは GitHub の Releases から利用者が自分で入れ直す (README) ので、版番号は利用者に見えている
  - SimpMusic (個人の Android アプリ): 1.0 にしたのは出来ではなく在り方の変化 (Android 専用 → 複数の OS) のため。「最終地点ではなく土台」
  - NewPipe: 0.29 まで 0.x のまま。1.0 にしない理由は見つからなかった
  - Element X (element.io): 2023-09 の Ignition は「管理者と早く試す人向け」「まだ今の Element アプリの完全な代わりではない」とし、
    "we'll obviously aim for a production ready 1.0 as soon as possible" と書いた。2024-10 の deep dive は番号を使わず
    "The Matrix Conference saw the official launch of Element X!"、"the mobile app that almost all Element users should be using"、
    "ready for primetime" と書いた。1.0 (正式な公開) を「本番で使える・皆が使うべきもの」として扱っている
  - Pantheon の記事は題名が「… for Libraries using SemVer」で、ライブラリ向け
- 要約だけで読んだもの (判断には使っていない): Rocket.Chat 1.0 は「思い描いた機能が揃った最初の版」、Mattermost 1.0 は「Slack と互換・セルフホストできる」
- 推測: 人が使うアプリでは 1.0 に共通の意味は無く、各アプリが決めている (例は少なく、偏っているかもしれない)。
  このアプリでは版番号が見えるので、0.x は「試作」と読まれている可能性がある (利用者の受け取り方は確かめていない)
- 出典: semver.org、pantheon.io「Don't Fear the 1.0」、runway.team「how-why-mobile-app-versioning」、photoroom.com「year-week-iteration」、
  simpmusic.org「why-i-changed-the-version-from-v0-to-v1」、newpipe.net (0.27.6 の告知)、element.io (Ignition・deep dive)。原文はすべて 2026-11-14 に読んだ

### 圏外の後に通信が固まるのは、このアプリだけか (#101)
- 入り口: #101 で「圏外の間に始めた WebSocket の試みが固まった」と推測したまま直した (D-064)。固まり方は OkHttp や Android でよく知られたものか、自分の作りの問題かを疑った
- 確かめたこと (原文を読んだ):
  - OkHttp の Issue #3278 (https://github.com/square/okhttp/issues/3278、「Network calls hang after coming back online after being offline」)。
    機内モードなどで圏外になり、つながり直した後に通信が固まる・時間切れになる報告が、主に Android のエミュレータで、一部は実機でも集まっている。
    保守者は「Android のエミュレータのネットワークは混乱していて、きれいには直せない」とし、OkHttp の外の問題と見ている。
    対策として保守者が挙げたのは「Android の回線の変化を購読する」こと (OkHttp では実装していない)。2025-08 にライブラリの直し無しで閉じられた
  - 同じ Issue で挙がった回避: 圏外の前の接続が使い回しの溜まり (connection pool) に残って古くなり、それを使うと固まる。
    つながり直した直後に 2 秒ほど置く、HTTP/1.1 に限る、時間の上限を付ける、などが報告されている (どれも一部の人に効いた、という報告)
  - OkHttp の Issue #5328 (Pixel 3 の機内モードで connectTimeout が効かない) は、VPN が手元の代理として接続を受けていたのが原因だった。今回とは別
- 推測: #101 の固まりは、#3278 と同じエミュレータの振る舞いの可能性が高い。D-064 (回線の復帰で固まった試みを捨てる・見張り) は、保守者が挙げた方向と同じ
- 残りの隙間 (推測): 回線が戻ったときに、HTTP の使い回しの溜まりを空にしていない。圏外の前の古い接続を HTTP の取得が使うと、#3278 と同じ形で固まりうる。
  e2e で HTTP の取得が固まった記録はまだ無い。次に起きたら、`connectionPool.evictAll()` を回線の復帰で呼ぶかを考える (ROADMAP に置く)
