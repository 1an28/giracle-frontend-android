### 送ったものは見えるべきか (自分の送信のあとの位置)
- 入り口: 「送った返信は画面に見える」は当たり前と思っていた。よく使う作業 (D-046) の「返す」を決めるときに、
  このアプリでは読んでいる途中で返すと、送った返信が画面の外 (一番下) に出て見えないことに気づいた (ChannelScreen は最下部にいるときだけ追従する)
- 確かめたこと: Element X Android (`develop` の `TimelineView.kt`) は、新しい出来事が自分のもの (`NewEventState.FromMe`) なら、
  読んでいる位置に関係なく一番下へ送る (`scrollToBottom(force = true)`。11 項目より離れていれば一気に、近ければ動かして)。
  他人のものは、下から 3 項目以内にいてライブのときだけ追従し、そうでなければ「最下部へ」のボタンに未読の印を付ける
- 推測: 自分が送ったものが見えないと、送れたかどうかを確かめるために、もう一度スクロールする手間が生まれる (P-3)。e2e の `reply` で見えるかを記録して確かめる
- e2e の reply で、判定を直した後 4 回とも返信が見えないことを確かめた (#57)。直す作業は #58
- 直した (D-051)。送れたら、そのメッセージが一覧に載るのを待ってから送る。最新側を読み込んでいなければ読み込み直す

### 自分の送信で一番下へ送るのを、嫌がる人はいないか
- 入り口: D-051 で「自分が送ったら一番下へ」を当たり前として直した。逆の意見が無いかを疑った
- 確かめたこと (検索結果の見出しと要約まで。原文は開いていない): 「送ると一番下へ飛んで、読んでいた位置を失う」という不満は、
  主に AI のチャット (Cursor・VS Code の拡張など) で出ている。そこでは長い答えが流れ込むのを読みながら、上の方も読み返すため
- 確かめたこと: MUI の Chat の説明 (mui.com) は、この環境から開けなかった (ネットワークの設定)。検索の要約では「自分の送信では常に送り、他は下から離れていれば止める」
- 推測: 人どうしのチャットで送るのは短い文で、送れたかを見たい。AI のチャットとは、送った後に見たいものが違う。
  ただ「返信を書く間、元のメッセージを見ていたい」はあり得る。送った後に元の位置へ戻す手段 (返信の引用を押すと元へ飛ぶ) はもうある

### Firebase Test Lab を無料のまま使えるか (D-048)
- 入り口: 「実機での速さは測れない」(D-045) を当たり前にしていた。持ち主との相談で、無料の実機の枠があると分かった
- 確かめたこと (gcloud 570.0.0 の `gcloud firebase test android run --help`): 実機の上限 45 分。結果の既定のバケットは無料で、
  使う主体に roles/editor が要る。自分のバケット (`--results-bucket`) は支払いの設定が要る。
  android/performance-samples の Test Lab のワークフロー (原文): Macrobenchmark の結果を `/sdcard/Download` に出して取り出している
- 要約で読んだこと (firebase.google.com・docs.cloud.google.com は開けなかった): Spark は実機 1 日 5 回・仮想 10 回で、支払い情報なしで使える。
  Cloud Storage for Firebase は 2026-02 から Blaze が必要。Test Lab は 2027-09-30 に終わり、後継 (Developer Device Platform) は支払いの設定が要る
- 推測: 支払い方法を登録しない限り、請求は起きない。Test Lab の終わりが本当なら、実機で測れるのは 2027-09 まで
- 気づいたこと: Test Lab の端末は CI のランナーのサーバーに届かない。これまでの計測 (エミュレータ) は「同じ機械の中にサーバーがある」前提に頼っていた

### 送信待ちの「届いていたか」の判定は正しいか (#66)
- 入り口: D-029 の弱点は「別の端末から同じ本文を続けて送ったとき」と書かれていた。弱点はそれだけか、を疑った
- 確かめたこと (コードを読んだ): `Outbox.alreadyDelivered` は送信者・本文・時刻 (最初に送ろうとした時刻 - 2 分以降) だけを比べ、添付と返信先を見ない。
  本文なしで画像を送ると本文は `""` なので、2 分以内に送った別の画像と一致し、送られずに消えうる。
  backend (`87be860`) の `message.service.ts` の Send (566 行目付近) は、添付のファイルが「自分がこのチャンネルへアップロードした未添付のもの」かを検証するので、
  添付付きはファイルの ID で確実に判定できる
- 推測: 画像だけの送信は、電波の悪い場所 (外出先で写真を送る) で起きやすい

### 保存の書き込みが重ならないか (#67)
- 入り口: 「一時ファイルに書いてから名前を変えれば壊れない」を当たり前にしていた
- 確かめたこと (コードを読んだ): 一時ファイルの名前が固定で、書き込みを排他していない。送信待ちは入力欄 (メインスレッド)・通知からの返信・送り直しの 3 か所から書く。
  名前を変える方式は「途中で落ちても壊れない」は守るが、「2 つが同時に書く」は守らない
