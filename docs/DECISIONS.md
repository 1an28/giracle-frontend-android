# 判断記録 (Decision Log)

このファイルには、開発中に自分で判断したことを時系列で残す。
各項目は「判断」「理由」「代替案」の順で書く。

---

## D-001 技術選定: Kotlin + Jetpack Compose (ネイティブ)

- **判断**: Kotlin によるネイティブ Android アプリとし、UI は Jetpack Compose (Material 3) で書く。
- **理由**
  - Flutter は Dart VM と描画エンジン (Impeller) をアプリに同梱するため、APK サイズとメモリが増え、
    起動時にエンジンの初期化が入る。同一アプリを Native(Compose)/KMP/Flutter で作り Macrobenchmark
    (Pixel 4a, 5 回) で比べた公開ベンチマーク
    (https://github.com/jacobras/flutter-vs-native-vs-kmp) では、起動時間の中央値が
    Native 413ms / Flutter 634ms、APK サイズが 1.46MB / 6.83MB だった。
  - Compose と従来の View (RecyclerView) の比較では、Google 公式の Hero benchmarks で
    「Compose 1.9 以降はスクロール時のジャンクが View と同等」とされている
    (https://developer.android.com/develop/ui/compose/performance)。Compose 単独の APK は
    View+AppCompat 構成と同程度のサイズ (公式 Sunflower 比較:
    https://developer.android.com/develop/ui/compose/migrate/compare-metrics)。
  - Compose は Google が推奨する現行の UI ツールキットで、今後も更新が続く。View(XML) は保守モード。
  - 「サポートが続いている技術」という条件に、Kotlin / Compose / AndroidX / OkHttp はいずれも合う。
- **代替案**
  - View(XML)+RecyclerView: 最速を突き詰められる余地はわずかにあるが、コード量が増え、保守モードの技術になる。
  - Kotlin Multiplatform / Compose Multiplatform: iOS も視野に入るが今回は Android のみなので不要。

## D-003 Flutter 版と同じ端末に並べて入れられるようにする

- Flutter 版の applicationId は `com.giracle.giracle`。本アプリは `com.giracle.android` とし (D-015 で変更)、
  アプリ名も「Giracle Native」にしてホーム画面で区別できるようにする。

## D-004 署名鍵をリポジトリに入れない

- リポジトリは公開 (public) のため、release 署名鍵はコミットしない。
  `keystore.properties` (gitignore 済み) があればそれで署名し、無ければ debug 鍵で署名する。
- 配布用 APK に使った鍵ファイルはユーザーに直接渡し、以後の更新ビルドで同じ鍵を使えるようにする。

## D-005 画面遷移はライブラリを使わず自前の小さなスタックにする

- **判断**: Navigation Compose を使わず、`ui/Nav.kt` の `Navigator` (画面のリスト) で遷移する。
- **理由**: 画面数が少なく、深いリンクや引数の複雑な受け渡しが不要。依存と初期化コストを減らせる。
  システムの「戻る」は `BackHandler` で処理し、チャンネル間の移動はスタックを積まずに置き換える。

## D-006 サーバー URL は Web 版と同じ配置 (`/api/` と `/ws`) を前提にする

- **判断**: ユーザーは `https://chat.example.com` のようにホストだけ入れる。HTTP は `/api/...`、
  WebSocket は `/ws` に接続する。開発用に「バックエンドへ直接接続 (`/api` を付けない)」も選べる。
- **理由**: Web 版 (giracle-frontend-solid) の vite.config.ts がこの配置でリバースプロキシしており、
  本番も同じ構成と考えられる。Flutter 版も同じ扱い (`/api` を自動付与)。
- **WebSocket の Origin**: バックエンドは Origin ヘッダが無いと 403、CORS_ORIGIN 設定時は一覧と一致しないと 403。
  ネイティブアプリには本来 Origin が無いため、サーバー URL から作った Origin (`https://chat.example.com`) を送る。
  Web 版と同じホストで運用していれば CORS_ORIGIN に含まれているはず。含まれていない場合は画面上部に案内を出す。
- **Origin の扱いは暫定**: アプリが Web 版の Origin を名乗って接続するのは、今のサーバーで動かすための仮の方法。
  アプリ向けの正式な接続方法 (サーバー側の入口) は友人 (サーバーの作者) と相談して決める予定 ([#7](https://github.com/1an28/giracle-frontend-kotlin/issues/7))。

## D-007 トークンは Cookie Jar を使わず自前で付ける

- **判断**: ログイン応答の `Set-Cookie: token=...` を取り出して保存し、HTTP・WebSocket・画像・ダウンロードの
  すべてに `Cookie: token=...` を付ける (OkHttp のインターセプタ 1 か所)。
- **理由**: 4 種類の通信で同じ認証を確実に共有でき、Cookie Jar より単純で速い。
  サーバーが期限延長で Cookie を再発行したら、その値で上書きする。

## D-008 状態管理は 1 つのストア + チャンネルごとの StateFlow

- **判断**: Web 版の stores と WS ハンドラをまとめた `ChatStore` を作る。履歴はチャンネルごとに別の StateFlow。
- **理由**: 表示中のチャンネル以外の更新で再描画が起きないようにするため。ユーザー名などは「その人の分だけ」購読する
  (`rememberUser`) ので、他人のプロフィール更新でメッセージ一覧全体が描き直されない。
- 履歴はメモリ上に最大 600 件。超えたら反対側を捨てる (Web 版は 120 件で切る。ネイティブのリストは
  見えている行しか描かないので多めに持てる)。

## D-009 起動の高速化

- 前回の状態 (チャンネル・ユーザー・各チャンネル最新 40 件など) を背面に回ったときに保存し、次回起動時は
  それを即座に表示してからサーバーの最新に置き換える。開いたチャンネルは必ずサーバーから取り直す
  (保存内容が古くても誤った表示が残らない)。
- アプリ本体の Baseline Profile を同梱する。実機での記録 (Macrobenchmark) は端末が無いためできず、
  アプリのパッケージ全体を対象にするワイルドカード規則にした。
  - 追記: リリースでは、CI のエミュレータで記録したものに置き換えるようにした (D-021)。
- R8 (縮小・難読化) とリソース縮小、翻訳リソースの日本語・英語限定で release APK は約 2MB。
- DI ライブラリなし、JSON は kotlinx.serialization (リフレクションなし)。

## D-010 通知の受け取り方 (D-019 で決定)

- 追記: アプリを閉じているときの標準は D-019 (UnifiedPush + 組み込み FCM 配信) に決めた。以下は決める前の記録。

- **アプリが前面のとき**: WebSocket の受信を画面上部のバナーで知らせる (Web 版のブラウザ通知に相当)。これは確定。
- **アプリを閉じているとき**: どの方法を標準にするかは **未決定**。着手するときに決める ([#6](https://github.com/1an28/giracle-frontend-kotlin/issues/6))。
  今は次の 2 つを、利用者が設定で選べる形で実装してある。
  - **UnifiedPush + 配信アプリ**: サーバーは既に Web Push (VAPID + aes128gcm) で通知を送れる。UnifiedPush の宛先は
    Web Push と同じ形式なので、`platform: "web"` の端末として登録すれば サーバーのコード変更なしで 届く。
    端末側に配信アプリ (ntfy など) が必要。サーバー管理者は VAPID 鍵を設定するだけ。
  - **常時接続**: 前面サービスで WebSocket を保ち続ける設定。配信アプリは不要だが電池を使う。
- **FCM (Google のプッシュ)** は、Firebase プロジェクトとサーバー側の実装が必要なため未実装。選ぶ場合はサーバーの
  変更を友人と相談する。必要な変更は SERVER_CHANGES.md の S-2 にまとめてある。

## D-012 検証方法

- 開発環境に Android 端末・エミュレータ (KVM なし) が無いため、次の 2 つで確かめる。
  - `LiveServerTest`: 実際のバックエンド (Web 版と同じ `/api` 構成) に 3 ユーザーでつなぎ、主要な操作と

## D-014 CI とリリース

- **CI の SDK**: `android-actions/setup-android@v3` は既定で廃止済みの SDK パッケージ `tools` を入れようとして
  失敗する (PR #1 の失敗の原因)。ランナーに最初から入っている Android SDK を使い、足りないパッケージだけ
  `.github/scripts/sdk-install.sh` で入れる。
- **リリース**: `v*` タグの push で `release.yml` が GitHub のリリースを作り APK を添付する。
- **署名**: CI が毎回生成する debug 鍵で署名すると、版ごとに鍵が変わり上書きインストールできなくなる。
  そのため、Secrets に署名鍵があれば CI で署名し、無ければリポジトリに置いた署名済み APK (`releases/`) を使う。
  どちらでも、署名証明書の指紋が `releases/SIGNING_CERT_SHA256` と一致しないときは公開しない。
  署名鍵はリポジトリの持ち主が Secrets に登録し、v0.1.0 から CI が署名している。リポジトリに置いていた
  署名済み APK は不要になったので削除した (Secrets が使えないときの予備の仕組みはワークフローに残す)。
- タグの push ができない環境 (このセッションの Git 権限) でも出せるよう、release ワークフローは手動実行にも対応し、
  そのときはワークフロー自身がタグを付ける。

## D-015 アプリの識別名 (applicationId) を持ち主の名前空間に移す

- **判断**: applicationId を `com.giracle.android` から `io.github.u1an28.giracle.kotlin` に変える
  (開発版は `.debug` が付く)。持ち主が方針を決め ([#9](https://github.com/1an28/giracle-frontend-kotlin/issues/9))、
  名前の形は「持ち主の名前と Kotlin 版であることが分かる」という条件で Claude が決めた。
- **理由**
  - `com.giracle.*` は Giracle の作者側の名前空間に見え、公式アプリが出たときにぶつかるおそれがある。
  - GitHub ユーザー名 `1an28` は数字で始まるが、applicationId の各部分は英字で始める決まりがあるため、先頭に `u` を付けた。
  - 識別名を変えると別アプリ扱いになり、入れてある版に上書き更新できない。利用者が少ない今のうちに変える。
- **変えなかったもの**: `namespace` とコードのパッケージ名 (`com.giracle.android`)。利用者からは見えず、
  変えても全ファイルの差分が増えるだけのため。署名鍵と証明書の指紋 (`releases/SIGNING_CERT_SHA256`) も変わらない。
- **利用者への影響**: 新しい版を入れ直してログインし直す。古い版 (`com.giracle.android`) は手で消す。
- **代替案**: `io.github.ian28...` のように読み替える、独自ドメインを使う。どちらも持ち主の名前とずれるため採らなかった。

## D-016 画面要素の名前 (testTag) と、実サーバーを使うテストの作り
([#11](https://github.com/1an28/giracle-frontend-kotlin/issues/11))

- **testTag を resource-id として公開する**: `Root` の根元で `testTagsAsResourceId = true` にする
  (`ui/common/TestTags.kt` の `exposeTestTags()`)。JVM 上のテスト (`UiScreenshotTest`) と、配布版を
  エミュレータで外から操作する確認 ([#12](https://github.com/1an28/giracle-frontend-kotlin/issues/12)、UI Automator の `By.res`) で
  同じ名前を使えるようにするため。ボトムシートとダイアログは別ウィンドウで根元の設定が届かないので、中身にも付ける。
  - 代償: 付けた要素の分だけ、アクセシビリティ情報に resource-id が増える。動作や見た目は変わらない。
- **名前の付け方**: すべて `TestTags` に定数・関数で置き、画面のコードとテストの両方がそこを参照する。
  形は「画面.要素」(`screen.home`、`composer.send`、`message_actions.emoji_picker`)。
  一覧の行のように同じ要素が並ぶものは「:ID」を付ける (`home.channel:<チャンネル ID>`、`channel.message:<メッセージ ID>`、
  `channel.reaction:<メッセージ ID>:<絵文字コード>`)。見た目の文言とは独立させ、文言を変えてもテストが壊れないようにする。
- **画面ごとのタグ**: 各画面は `Root` で `screen.*` のタグ付きの箱に包む。画面ごとのファイルに手を入れずに済み、
  「どの画面にいるか」を一か所で決められる。
- **専用チャンネル**: `UiScreenshotTest` はテストごとに専用のチャンネルを作ってメッセージを入れ、終わったら消す。
  `seed-demo.sh` のデータや他のテストの投稿に左右されない。必要なのは管理者アカウントだけ。
- **待ち合わせ**: `Thread.sleep` をやめ、要素が現れる・消えるまで `waitUntil` で待つ形にそろえた。
  画像の読み込み完了は画面の情報 (semantics) に出ないので待っておらず、スクリーンショットで画像が読み込み途中のことがある。
  - 追記 (#20): 添付画像は、読み込みが済むと testTag が `channel.image:<ファイル ID>` から `channel.image_loaded:<ファイル ID>` に変わる
    ようにした。e2e はこれで読み込み完了を待つ。
- **テストの規則 (v2)**: `androidx.compose.ui.test.junit4.v2.createAndroidComposeRule` に移った。
- **CI で実サーバーのテストを動かす**: `live-test.yml` がランナー上に `devtools/start-local-stack.sh` でサーバーを立て、
  管理者を作ってから `GIRACLE_TEST_SERVER` 付きでテストを動かす。スクリーンショットは成果物 (`screenshots`) に残す。
  開発環境に Android SDK が無く手元で動かせないため、ここで確かめる。
  - サーバーは参照先 (giracle-backend / giracle-frontend-solid) の最新版を毎回取ってくるので、相手側の変更で
    失敗することがある。アプリのビルドと単体テスト (`build.yml`) とは別のワークフローにして、どちらが原因か分かるようにした。
  - 代替案: 参照先の版を固定する。相手側の変更に気づくのが遅れるので、今は固定しない。

## D-017 直前のメッセージの編集は長押しメニューのままにする

- **判断**: スマホ向けに新しい操作 (編集ボタン・スワイプ・↑ キー) は足さず、長押しメニューの「編集」で編集する
  ([#5](https://github.com/1an28/giracle-frontend-kotlin/issues/5))。持ち主が判断を Claude に任せた。
- **理由**
  - 長押しメニューから 1 回のタップで編集に入れ、編集中は入力欄の上に表示が出るので、足りている。
  - 入力欄の周りにボタンを増やすと、送信や添付の押し間違いが増える。スワイプは返信など他の操作と取り合いになる。
  - 実機で使ってみて不便だと分かったら、そのとき Issue を開き直す。
- **代替案**: 入力欄が空のときの「直前のメッセージを編集」ボタン、送信直後の「編集」ボタン、スワイプ、外付けキーボードの ↑ キー。

## D-018 配布版をエミュレータで外から確かめる (e2e)
([#12](https://github.com/1an28/giracle-frontend-kotlin/issues/12))

- **GitHub Actions でエミュレータが動くか (確かめた)**: `ubuntu-latest` (2026-11 時点で ubuntu-26.04、4 コア・メモリ 15GB) に
  `/dev/kvm` があり、権限を開ければ使える。エミュレータ自身の判定も「KVM (version 12) is installed and usable」。
  Android 15 (API 35、google_apis、x86_64) の起動は 27〜40 秒、SDK 一式の取得は 30〜50 秒。
  - つまずいた点: `sdkmanager` は入れるときにもライセンスの同意を求めて入力待ちで止まる (`yes` を渡す)。
    `avdmanager` と `emulator` で AVD の置き場所の解釈がずれる (`ANDROID_AVD_HOME` を明示)。
    起動直後はホーム画面アプリの「応答していません」ダイアログが出て画面を覆う (`hide_error_dialogs` で出さず、テスト側でも閉じる)。
- **作り**:
  - `:e2e` モジュール (`com.android.test` + self-instrumenting)。UI Automator で、配布版 APK を **外から** 操作する。
    アプリのコードには依存せず、要素は D-016 の testTag (resource-id) で探す。self-instrumenting なので、アプリと同じ鍵で署名しなくてよい。
  - 配布版は debug 鍵で署名した `assembleRelease` を使う (R8 の処理は本物の配布版と同じ。Secrets は使わない)。
  - サーバーは `live-test` と同じ composite action (`.github/actions/local-server`) で立てる。端末の `localhost:3333` を
    `adb reverse` でランナーのサーバーにつなぐので、アプリが送る Origin が CORS_ORIGIN (`http://localhost:3333`) と一致する。
  - テストの準備 (相手役ユーザー・チャンネルの作成) と相手側の送信は、テストがサーバーの API を直接呼ぶ。
  - 手順は `ReleaseAppTest` の 1 本の流れ: まっさらな状態から起動 → サーバー指定・ログイン → 通知の権限を許可 →
    チャンネルを開く → 送信 (画面とサーバーの両方で確認) → 相手の送信を WebSocket で受信 → 背面に回して戻る
    (背面の間の投稿の取り直しと、戻った後の受信) → 常時接続 (前面サービス) を ON → 背面でメンションが通知される。
    各段階でアプリのプロセスが生きていることと、crash バッファに記録が無いことを確かめる。
  - 失敗したときは、logcat の要点・crash バッファ・終了時点の画面の要素一覧を CI のログに直接出す
    (成果物の zip はこの開発環境から取得できないため)。画面の PNG・logcat 全体・mapping.txt は成果物 `e2e` に残す。
- **見つかった不具合 (直した)**: 初回ログインの直後に必ず「サーバーから読み込めませんでした」になっていた (v0.2.0 にもある。
  「再試行」で直る)。ログイン画面の scope で読み込んでいたため、ログイン画面が外れると読み込みが取り消され、それを失敗として
  表示していた。R8 とは無関係で、JVM 上のテストはログイン画面を通らないので気づけなかった。読み込みをアプリの scope に移した。
- **R8 について**: 上の流れで、配布版が起動し、JSON の変換・WebSocket・前面サービス・通知まで動くことを確かめた。
  画像の表示・リアクション・ファイルの送信・UnifiedPush は通していないので、R8 で壊れていないかは未確認。
- **実行するタイミング**: PR ごと・main への push・手動実行。
  - 理由: 公開リポジトリなので標準ランナーは無料で、時間 (1 回約 7〜8 分) も他のワークフローと並んで走るので待ち時間は増えない。
    初回から実際の不具合を見つけており、R8 の設定や依存の更新はどの PR でも配布版を壊しうるので、毎回確かめる価値がある。
  - 同じブランチに続けて push したときは、古い実行を取り消す (`concurrency`)。
  - 失敗が続く・不安定になる場合の代替案: main への push と手動実行だけにする。
- **#8 (Baseline Profile) で流用できるもの**: エミュレータの起動 (`.github/scripts/emulator-start.sh`)、サーバー
  (`.github/actions/local-server`)、`com.android.test` + self-instrumenting のモジュールの形 (`e2e/build.gradle.kts`)。
  Baseline Profile Gradle Plugin は Gradle 管理の端末も使えるが、ここでは同じ起動スクリプトを使えば、サーバーの用意も共有できる。

## D-019 プッシュ通知の標準: UnifiedPush + 組み込み FCM 配信 (配信アプリ不要)
([#6](https://github.com/1an28/giracle-frontend-kotlin/issues/6)。D-010 の「未決定」をこれで決める)

- **きっかけ (持ち主がサーバーの作者と話した内容、2026-11-12)**: 通知を誰が決め、誰が実装するかは決まっていなかった。
  ntfy を使うことには賛否があった。サーバーの作者は「VAPID 鍵はあるので、やろうと思えばすぐできそう」
  「アプリで完結してほしいなら、Firebase か何かを使いたい」という意見だった。
- **判断**: UnifiedPush の **組み込み FCM 配信** (`org.unifiedpush.android:embedded-fcm-distributor` 3.1.0) を入れ、
  これを標準にする。ログイン後に自動で有効にする。配信アプリ (ntfy など) が入っている端末ではそちらを優先する。
  常時接続は、Google Play 開発者サービスも配信アプリも無い端末向けに残す。
- **仕組み (ライブラリのソースで確かめた)**:
  - アプリが Google Play 開発者サービスに、サーバーの **VAPID 公開鍵を送信者として** 登録する。
    宛先 `https://fcm.googleapis.com/fcm/send/<トークン>` が返ってくる (Chrome の Web Push と同じ種類の宛先)。
  - アプリはその宛先と鍵を、今までどおり `platform: "web"` の端末としてサーバーに登録する。
  - サーバーは今の Web Push (VAPID + aes128gcm) のまま送る。FCM は VAPID 付きの Web Push をそのまま受け付ける。
    中身は端末の鍵で暗号化されたまま届き、アプリが復号する (Google には暗号文しか見えない)。
  - **Firebase プロジェクト・`google-services.json`・サーバーのコード変更は、どれも要らない**。
    ライブラリは Firebase SDK を使わず、Play 開発者サービスと直接やり取りする (依存は Kotlin 標準ライブラリとコルーチンだけ、約 64KB)。
- **理由**
  - 「アプリで完結」(配信アプリ不要) と「サーバーは VAPID があればすぐできる」の両方を、サーバーを変えずに満たせる。
  - Firebase を使う案 (S-2 の FCM 案) は、Firebase プロジェクトを誰が持つか・サーバーに鍵を置くか・実装を誰がやるかを
    決める必要があり、まさに決まっていない部分だった。この方法ならその判断自体が要らない。
  - ntfy に反対の人には、ntfy を入れずに済む。賛成の人は、ntfy を入れればそちらが使われる。
- **自動で有効にする条件**: 利用者が設定で無効にしていない・通知の権限がある・配信先が 1 つに決まる
  (配信アプリが複数あって選ぶ画面が要る場合は、設定から選んでもらう)。サーバーに VAPID 鍵が無ければ何もしない。
- **e2e で見つけて直した不具合**: プッシュでアプリのプロセスが裏から起きたとき、通知が出なかった。
  「画面が前面にあるか」の初期値が true のままで (画面の切り替えが一度も起きないため)、プッシュを「画面内で知らせる」扱いで捨てていた。
  また、裏で起きたプロセスがサーバーからの読み込みと WebSocket の接続を始め、つなぎっぱなしになっていた (電池・通信量の無駄)。
  前面の初期値を false にし、読み込みと接続は画面を開いたとき・常時接続のときだけ始めるようにした (`AppGraph.ensureSessionLoaded`)。
- **e2e で見つけて直した不具合 (2)**: ログイン直後に、画面が 20 秒以上固まることがあった。プッシュの登録 (`UnifiedPush.register`) は
  Android Keystore で鍵を作り、それを画面の処理の流れ (メインスレッド) で呼んでいた。エミュレータの起動直後は Keystore が遅い。
  登録・解除を別スレッド (Dispatchers.IO) で行うようにした。実機でどのくらいかかるかは未計測。
- **あわせて直したこと**: ログアウトしてもサーバーに端末の登録が残り、前のユーザー宛ての通知が届き続けていた。
  ログアウトの前にサーバーから登録を消し、配信先の登録も解くようにした。
- **確かめたこと**: CI のエミュレータ (Android 15、google_apis) で、ローカルのサーバー (VAPID 鍵を設定) を使い、
  ログイン後に自動で有効になること・アプリのプロセスが無い状態でメンションのプッシュ通知が届くことを確かめる (e2e の 9 番目の段階)。
- **確かめていないこと・注意**
  - 本番 (chat.girak.moe) から `fcm.googleapis.com` へ送れるか。Web 版の利用者が Chrome でプッシュ通知を使えていれば同じ宛先なので送れるはず (推測)。
  - このライブラリは Google の公開 API ではなく、Play 開発者サービスの内部のやり取りを使っている。Google 側の変更で
    動かなくなる可能性がある。その場合の代わりは、配信アプリ・常時接続・Firebase を使う方法 (S-2)。
  - サーバーが VAPID 鍵を作り直すと、登録をやり直す必要がある (アプリの設定の「再登録」)。
- **追記 (2026-11-13、持ち主がサーバーの作者と話した内容)**: サーバーの作者の方針は「Apple 向けは APNs、Web と Android は Web Push」。
  「Android」がネイティブアプリも含むと受け取ると (こちらの解釈)、この判断 (Android は `platform: "web"` の Web Push で受ける) と合うので、アプリは何も変えない。
  Android のブラウザで開く Web 版だけを指していた場合も、サーバーの変更が要らないことは同じ。
  - backend (`87be860`) は `platform` に `"android"` / `"ios"` も受け付けるが、送信は `"web"` だけ。
    iOS 対応で `"ios"` (APNs) の送信が足されても、`"web"` 宛ての送り方が変わらなければアプリには影響しない (コードを読んだうえでの推測)。
  - アプリが読むプッシュの中身は `title` / `body` / `tag` / `data.channelId` / `data.messageId`。送信処理を分けるときに
    この形が変わらないことだけ、サーバーの作者に伝えておく (SERVER_CHANGES S-2)。
- **代替案**: Firebase Messaging SDK + サーバーに FCM の送信を足す (S-2 の旧案。Firebase プロジェクトとサーバーの変更が要る)、
  配信アプリ (ntfy) だけ、常時接続だけ。

## D-020 画像の貼り付け: キーボードからの画像入力と、他のアプリからの共有を足す
([#4](https://github.com/1an28/giracle-frontend-kotlin/issues/4))

- **判断**: 次の 2 つを足す。既存の添付ボタンは変えない。
  - **キーボードからの画像入力・貼り付け**: 入力欄で、キーボード (Gboard など) の画像・GIF・ステッカーの挿入と、
    長押しメニューの「貼り付け」で入る画像を、添付として受け取る (Compose の `contentReceiver`)。文字の貼り付けは今までどおり入力欄に入る。
    編集中は添付できないので受けない。
  - **他のアプリからの共有**: 「共有」の送り先に Giracle Native を出す (画像・動画・ファイル・文章。1 件でも複数でも)。
    受け取るとホーム画面に「送るチャンネルを選んでください」と出し、選んだチャンネルの入力欄に添付 (アップロード開始) と文章を入れる。
    送る前に文章を足したり、添付を外したりできる。
- **理由**
  - スマホで画像を送る場面は「キーボードの GIF・ステッカー」「スクリーンショットやギャラリーから共有」が多い。
    クリップボードの画像の貼り付け (Web 版の `onPaste`) は、Android では長押しメニューの貼り付けで同じ流れに乗る。
  - 共有の送り先を先に固定 (最後に開いたチャンネルなど) せず選ばせるのは、誤送信を避けるため。
- **作りの変更**: 入力欄を `TextFieldValue` から `TextFieldState` に移した (`contentReceiver` は `TextFieldState` を使う入力欄だけが対応するため)。
  メンション候補・下書き・編集の扱いは同じ。
- **確かめたこと**: e2e で、共有 (画像と文書ファイルの 2 件 + 文章) → ホームで送り先を選ぶ → アップロード → 送信 →
  サーバーに添付 2 件で届く → 画像が読み込まれて表示される → 文書ファイルが表示される、まで通す (#20 も兼ねる)。
- **確かめていないこと**: キーボードからの画像の挿入 (エミュレータの UI Automator では、キーボードの画像挿入を起こせない)。
  実機で Gboard の GIF・ステッカーを入れたときの動き。
- **代替案**: 共有は最後に開いたチャンネルへ直接入れる (速いが誤送信しやすい)。貼り付けは添付ボタンだけのまま。

## D-022 通知からの返信・既読、下書きの保存、管理者のパスワードリセット

- **通知の「返信」「既読にする」**: 通知にボタンを付け、アプリを開かずに返信・既読ができるようにした (`NotificationActionReceiver`)。
  - 返信は、通知のメッセージへの返信 (`replyingMessageId` 付き) として送る。スマホでは「その発言への返事」が自然なため。
    代替案: チャンネルへの普通の投稿にする。
  - 返信・既読のどちらでも、そのメッセージの通知 (Inbox) を既読にし、チャンネルの既読位置をそのメッセージまで進める (今より前には戻さない)。
  - 失敗したら、通知を「送れませんでした」に置き換えて知らせる (内容は消えるので、アプリから送り直してもらう)。
  - 確かめていない: 実機での操作 (e2e では通知のボタンの入力を通していない)。
- **通知を会話の形にする** ([#26](https://github.com/1an28/giracle-frontend-kotlin/issues/26) のアプリ側): チャンネルごとに 1 つの通知にまとめ、
  `MessagingStyle` で送信者名と最近のメッセージ (8 件まで) を並べる。そのチャンネルを開くと通知を消す。
  プッシュの送信者名は、題 (「<名前> さんからのメンション」) から取り出す。送信者のアイコンは未対応 (S-7 の返事を待つ)。
- **下書きの保存**: チャンネルごとの下書きを、打つ手が止まってから端末に保存するようにした (今まではアプリのプロセスが終わると消えた)。
  ログアウトで消す。
- **管理者によるパスワードのリセット**: サーバーにある `POST /user/reset-password` (Web 版は使っていない) を、メンバーの詳細に足した。
  サーバー管理の権限 (manageServer) があり、自分より下のロールの人だけが対象 (サーバー側の判定)。新しいパスワードはサーバーが作り、
  その場で表示・コピーできる。スマホしか持っていない管理者が、パスワードを忘れた人を助けられるようにするため。
  - `LiveServerTest.adminResetsPassword` で、新しいパスワードでログインでき、古いものは使えなくなることを確かめる。

## D-023 最近送ったチャンネルを、共有シートの直接の送り先にする
([#25](https://github.com/1an28/giracle-frontend-kotlin/issues/25))

- **判断**: メッセージを送ったチャンネルを、端末の動的ショートカット (長期) として登録する。共有シートの上段に直接の送り先として出て、
  選ぶとホームを経由せずにそのチャンネルの入力欄に入る (D-020 の流れの短縮)。ランチャーのアイコンの長押しからも、そのチャンネルを開ける。
- **登録するのは送信したときだけ**: チャンネルを開くたびに登録すると、ショートカットの書き込みが増えて重い。よく送る先が残れば十分。
- ログアウトで消す (別のアカウントのチャンネルを出さないため)。
- 共有シートの直接の送り先は Android 10 以降の仕組み。それより前の端末では、今までどおり「Giracle Native」を選んでからチャンネルを選ぶ。
- **確かめていないこと**: 共有シートの見た目と、直接の送り先を選んだときの動き (e2e は共有のインテントを直接送っており、共有シートを通していない)。

## D-025 送る写真を縮小する (#28)

- **判断**: 設定「送る写真を縮小する」(既定 ON) を足す。JPEG・HEIC/HEIF は長辺 2048px・JPEG 品質 85 に縮める。
  PNG は、透過が無く長辺が 2048px を超えるもの (スマホのスクリーンショットなど) だけを縮める。GIF・WebP・動画は縮めない
  (アニメーションが消えるため)。縮めても元より小さくならないときは元のまま送る。
- 縮小は送る前にアプリ内で行う (Android 9 以降は `ImageDecoder`、失敗したときと Android 8 は `BitmapFactory` + Exif の向き)。
  Bitmap から作り直すので、位置情報などの撮影情報 (Exif) は送られない。設定の説明にそう書いた。
- サイズの上限 (`messageMaxFileSize`) は、縮める写真は縮めた後の大きさで確かめる (縮めれば送れる写真を、選んだ時点で断らない)。
- **確かめたこと**: JVM のテスト (`ImageShrinkerTest`、Robolectric の実際の画像処理) で、3000×2000 の JPEG が 2048×1365 になり小さくなること、
  小さい PNG・透過のある PNG はそのまま送ること。
- **確かめていないこと**: `ImageDecoder` の経路 (Robolectric が対応していない)、HEIC、縮小にかかる時間 (端末で数百 ms の見込み)。
- 代替案: 長辺・品質を選べるようにする (今は ON/OFF だけ。要望があれば足す)。

## D-029 電波が無いときに送ったメッセージを、つながってから送る (#30)

- **判断**: 送信がネットワークの失敗 (`IOException`。サーバーに断られた `ApiException` は除く) で失敗したら、入力欄に戻さず
  「送信待ち」に入れる。送信待ちは端末のファイル (`outbox.json`) に保存し、アプリを閉じても残る。ログアウトで消す。
- WebSocket がつながったときに、古い順に送る。途中でまたネットワークで失敗したら、そこで止める (後の分も送れないため)。
  サーバーに断られたもの (チャンネルが消えたなど) は理由を出して残し、自動では送り直さない。
- 送信待ちは、入力欄の上に「送信待ち」として本文と「今すぐ送る」「取り消す」を出す。
  Issue の案 (履歴の末尾に薄く出し、長押しで選ぶ) より作りが小さく、履歴の一覧の仕組み (並び・既読・スクロール) に手を入れずに済むため。
- 二重送信を減らすため、送り直す前にそのチャンネルの最近 30 件を取り、自分が同じ本文を「最初に送ろうとした時刻 - 2 分」以降に
  送っていれば、届いていたとみなして送らない (送ったが応答が返らなかった場合)。
  弱点: 同じ本文 (「了解」など) を別の端末から続けて送った場合に、届いていたと取り違える。サーバーが送信に ID を付けられるようになれば (S-8) 確実にできる。
- 通知からの返信も、電波が無ければ送信待ちに入れ、通知でそう知らせる。
- 添付ファイル付きは、アップロードが済んだもの (ファイル ID があるもの) だけを送信待ちにできる (アップロード自体の失敗は今までどおり添付の欄にエラーを出す)。
- **確かめたこと**: JVM のテスト (`OutboxTest`) で、順に送ること・作り直しても残ること・電波が無ければ止まること・断られたものを自動で送らないこと・
  届いていたものを送らないこと。
- **確かめていないこと**: 実際に電波を切った端末での動き (e2e のエミュレータで機内モードにする確認は作っていない)。
  → #37 で、e2e が `10.0.2.2` (端末の通信網を通る経路) で機内モードにして確かめるようにした (`lanServerPermissionAndOfflineSend`)。
  `adb reverse` の `localhost` は端末の通信網を通らず、機内モードでも切れないため、こちらを使う。

## D-031 Android 17 のローカルネットワーク権限は、接続先が LAN のときだけ求める (#42)

- **背景 (確かめたこと)**: targetSdk 37 (Android 17) のアプリは、LAN のアドレスへの通信に実行時権限 `ACCESS_LOCAL_NETWORK`
  (権限グループ「付近のデバイス」) が要る。OkHttp を含むすべての通信が対象で、権限が無いと TCP はタイムアウトになる
  ([公式](https://developer.android.com/privacy-and-security/local-network-permission))。このアプリは v0.4.0 まで宣言していなかった。
- **判断**: マニフェストで宣言し、接続先のホストが LAN (プライベート IPv4・リンクローカル・IPv6 ULA、`.local` `.lan` `.home.arpa` `.internal`、
  点の無い名前、または名前を解決した結果が LAN のアドレス) のときだけ、接続の前に求める。インターネット上のサーバーしか使わない人には尋ねない。
  - ログイン画面: 「接続」を押したとき。拒否されたら理由と「アプリの設定を開く」を出す
  - ログイン済み (前の版から更新した人): 起動時に求め、許可されたら失敗していた読み込みをやり直す。読み込みの失敗画面にも理由を出す
  - 通知の権限は、こちらの答えが出てから尋ねる (確認画面を重ねない)
- ループバック (`localhost`。e2e の `adb reverse`) は対象外として扱う。
- 案「NSD の端末選択 (`FLAG_SHOW_PICKER`) で権限なしにつなぐ」は、mDNS でサーバーを公開している人しか使えないので採らない。
- **確かめたこと**: JVM のテスト (`LocalNetworkTest`) でアドレスと名前の判定。e2e を API 37 のエミュレータでも動かし、
  `http://10.0.2.2:3333` で確認画面が出ること・拒否で理由が出ること・許可でつながることを確かめる (`lanServerPermissionAndOfflineSend`)。
- **確かめていないこと**: Tailscale などの VPN のアドレス (100.64.0.0/10) が LAN 扱いになるか (今の判定では LAN としない)。
  名前解決に時間がかかる環境で「接続」の反応が遅れるか。

## D-032 回転・画面サイズの変更では Activity を作り直さず、画面の履歴も保存する (#39)

- **見つけたこと**: `MainActivity` に `configChanges` が無く、回転・折りたたみの開閉で Activity が作り直されていた。

- **判断**:

    (Android 17 では作り直したときにキーボードの表示が戻らなくなったので、その対策にもなる)。言語の変更と、ダーク/ライトの切り替え (uiMode) は対象にしない

## D-034 回線が戻ったら、再接続の待ち時間を待たずにつなぎ直す

- **見つけたこと**: `WsClient.nudge()` (すぐつなぎ直す) はどこからも呼ばれていなかった。切断の後は最大 30 秒の待ち時間 (指数バックオフ) を
  待ってからつなぎ直すため、機内モードを解除しても、送信待ち (D-029) が送られるまで最大 30 秒かかっていた。
- **判断**: `ConnectivityManager.registerDefaultNetworkCallback` で回線がつながったことを受け、`nudge()` を呼ぶ
  (`ACCESS_NETWORK_STATE` を宣言。利用者に尋ねない権限)。切断中でなければ何もしない。
- **確かめたこと**: e2e で、電波を戻してから送信待ちが届くまで約 2 秒 (2026-11-13 の main。API 37 で 2130ms、API 35 で 1790ms)。
  以前の作りなら、待ち時間の分 (最大 30 秒) かかっていた。

## D-036 想定していない例外でアプリを落とさない

- **見つけたこと** (コードを読んで見つけた): 次の 2 か所で、通信の失敗がどこにも捕まらずにアプリが落ちていた。
  - 通知から開いたとき (メッセージへ移動) に圏外だと、`jumpToMessage` がサーバーの拒否 (`ApiException`) しか捕まえておらず、
    接続の失敗 (`IOException`) が画面の処理の外まで抜けていた
  - WebSocket の再接続の直後の再同期で、開いているチャンネルの取り直しが失敗すると、例外が購読の外まで抜けていた
    (しかも取り直す前に表示を空にしていたので、落ちなくても読み込み中のまま止まる作りだった)
  - あわせて、ログアウトしても古いストアの購読 (再接続・接続状態) が止まらず、ログインし直すたびに増えていたのを直した
- **判断**:
  - 移動に失敗したときは、理由 (圏外など) を出して終わる
  - 再同期では、開いているチャンネルの表示を残したまま取り直す。失敗したら表示はそのままにし、次に開いたときに取り直す
  - アプリ全体の裏の処理 (`AppGraph.scope`) に、例外を記録だけする処理器を付ける。1 つの処理の想定外の例外で、アプリごと落ちないようにする。
    記録は logcat の `GiracleUncaught` に出る。crash バッファには出なくなるので、e2e (`e2e-run.sh`) はこの記録が出たら失敗にする
  - 送信 (と編集) を、画面ではなくアプリの scope で行う。以前は画面の scope で送っており、送ってすぐ「戻る」を押すと送信が取り消され、
    入力欄は送る前に空にしているので本文が消えていた。サーバーに断られたときは、画面を離れていても下書きに本文を戻す
- **確かめたこと**: `ChatStoreOfflineTest` (閉じたポートにつなぐ) で、再同期が例外を出さず、表示中のメッセージが残ること。
  単体・結合・画面のテストが、送信をアプリの scope に移した後も通ること。
- **確かめていないこと**: 通知から圏外で開いたときの動き (移動の件はテストで再現していない)。送ってすぐ戻ったときに届くこと (画面の操作では試していない)。

## D-037 画像の全画面表示に、保存・ダブルタップでの拡大を足す

- **見つけたこと**: 全画面表示は、ピンチで拡大できるだけだった。保存するには一度閉じて、添付の「ダウンロード」を探す必要があった
  (画像を自動で読み込む設定では、ダウンロードのボタンが出ない)。拡大すると画像の外まで動かせ、拡大しても画面の大きさでしか読み込まないので粗かった。
- **判断**: 全画面表示の右上に「保存」(添付のダウンロードと同じ。端末の「ダウンロード」へ) と「閉じる」を置く。
  ダブルタップで、押した所を中心に 2.5 倍と等倍を切り替える。拡大中は、画面に収めたときの画像の大きさから動かせる幅を決め、
  画像の端より外へ動かせなくする (画像を読み込む前は画面の大きさで代わりに計算する)。
  読み込みは画面の 2 倍 (長辺 1024〜4096px) までにし、元の画像より大きくは読まない (`Precision.INEXACT`)。
  小さい画像を引き伸ばして読むと、メモリを多く使うため (Coil は大きさを指定すると既定で引き伸ばす)。
  同じ理由で、一覧の画像も引き伸ばして読まないようにした。全画面表示の画像はメモリのキャッシュを一覧と分け、
  一覧が大きい方の画像を使い回してメモリを握り続けないようにした。
- **しなかったこと**: 他のアプリへの共有 (ファイルを渡す仕組み FileProvider の追加が要る。要望があれば足す)。
- **確かめたこと**: `UiScreenshotTest.imageViewer` で、開いて「閉じる」で閉じること (Robolectric では画像そのものは描かれない)。
  e2e (`ReleaseAppTest`) で、配布版で画像を押すと全画面で開き、戻るで閉じること。
- **確かめていないこと**: ダブルタップ・ピンチの操作感 (自動テストでは押していない)。

## D-038 通知を払って消したら、まとめていた会話も忘れる

- **見つけたこと** (コードを読んで): チャンネルごとの通知 (D-026) は、最近の発言を覚えておいて並べる。払って消しても覚えたままなので、
  次の通知に、払って消したはずの発言 (最大 8 件) がまた並んでいた。
- **判断**: 通知に削除の知らせ (deleteIntent) を付け、払って消されたら、そのチャンネルの覚えている発言を忘れる。
- **確かめたこと**: `NotifierTest` (Robolectric) で、2 件まとめた後に忘れると、次の通知が 1 件だけになること。削除の知らせが付いていること。
- **確かめていないこと**: 実際に払って消したときに知らせが届くこと (端末の通知欄は操作していない)。

## D-039 壁紙の色 (Material You) を選べるようにする

- **判断**: 表示の設定に「壁紙の色を使う」を足す (Android 12 以降だけ出す)。既定は OFF (今までどおり、Web 版に近い白黒基調)。

## D-040 ホームに「すべて既読」を置く

- **判断**: 未読のチャンネルがあるとき、ホームの上に「すべて既読にする」を出す (押すと確認してから既読にする)。Web 版には無い。

## D-041 添付を他のアプリへ共有する (#50)

## D-042 別の端末で既読にしたら、通知を消す (#49)

- **判断**: 通知にメッセージの時刻を持たせ、既読時刻がそれ以降になったチャンネルの通知を消す (#49 の選択肢 A と B)。
  既読時刻は、つながっている間の WebSocket (`ReadTimeUpdated`。常時接続のとき) と、前面に戻ったときの読み込み直しで更新される。
  プッシュで受けた通知は、メッセージを取って時刻を調べる (送信者を調べるのと同じ問い合わせ)。間に合わなかったときは時刻が無く、消さない。
  通知から返信した会話の通知は、返信で既読時刻が進んでも消さない (#38 の「返信したら会話に足して残す」を守る)。
- **しなかったこと**: サーバーから既読の更新をプッシュで送ってもらう (#49 の選択肢 C。サーバー側の変更が要る)。
- **制限**: 出した通知の覚えはメモリにしか無い。アプリのプロセスが作り直されると、それより前に出した通知は既読になっても消えない。
- **確かめたこと**: `NotifierTest.readElsewhereCancels` で、通知より前の既読時刻では消さず、通知のメッセージまで既読になったら消すこと。
- **確かめていないこと**: 実際に別の端末で既読にしたときの動き。

- **確かめていないこと**: 実機での操作感 (縦のスクロールとの取り合い・振動・画面の端からの操作との取り合い)。

## D-044 ホームのチャンネルの並べ替えを、引いて動かせるようにする

## D-045 UI の原則を、世の中の情報から決める (docs/UI_PRINCIPLES.md)

- **判断**: Web 版・Flutter 版をなぞる前提をやめ、研究・公式の基準・他社アプリの作り・ストアレビューから UI の原則を決めた。
  詳しい調査・出典・画面の点検・作り直す案は docs/UI_PRINCIPLES.md にある。原則は次の 7 つ。
  - P-1 待たせない (一度見たものはすぐ出し、裏で取り直す。スケルトンは使わない)
  - P-2 つながっていなくても読める・書ける
  - P-3 よく使う操作 (読む・返す・自分宛て・切り替える・探す) は 2 手以内、画面の上の隅に置かない
  - P-4 押せる範囲は 48dp 以上 (隣と重ならないこと)
  - P-5 一覧の場所を奪わない (常に出る帯は、行き先が 3 つ以上で行き来が多いときだけ)
  - P-6 配置を変えたら、手数と時間で比べる
  - P-7 どのチャンネルから読むかを、開かずに決められる材料を一覧に出す
- **前提 (持ち主との相談、2026-11)**: 持ち主の感覚・実機の操作は材料にしない (D-024)。今の配置を守ることに価値を置かない。
  M3 Expressive の調査は根拠にしない。Discord の 2023 年の反発は「遅さ」「よく使う操作が遠くなった」を教訓にする。
- **主な根拠**: Nielsen の 0.1/1/10 秒、Android の 48dp・16ms・700ms・起動の秒数、Parhi 2006 (親指 9.2mm)、
  Hoober (中央 7mm・隅 12mm、親指の届く範囲の図は誤り)、Viget 2017 (スケルトンが最も遅く感じられた)、
  Element X・Signal のコード、Slack 2020・Discord 2023・Telegram 2026 の刷新とその反応、
  Telegram・WhatsApp の低評価レビュー (160 件を読んで分類。配置への不満は少なく、「つながらず読めない」が多い)。
  多くは開発環境から原文を開けず、検索の要約で読んだ (UI_PRINCIPLES.md に「(要約)」と印を付けた)。
- **CI で確かめる仕組み**: Compose の `enableAccessibilityChecks()` (Accessibility Test Framework) を Robolectric で試したが、
  働かなかった。ATF が作る画面の構造に Compose の中身が入らない (`ComposeView` の下に 0×0 の要素が 1 つだけ。
  読み上げを有効にしても同じ)。公式の例 (ラベルが空) も見つけない。
  代わりに、Compose の意味情報から押せる範囲を測る検査を作った (`TouchTargets.kt`)。Compose は小さい押せる要素の範囲を
  48dp まで自動で広げる (押せる親の中でも広がるが、すぐ横・真下の別の押せる要素には負ける。Surface の後ろの層には取られない) ので、広げた範囲に、同じウィンドウの隣の押せる要素が入り込むものだけを数える。引く操作だけの要素は映らない。`UiScreenshotTest` で画面を撮るたびに調べ、
  CI (live-test) の最後に一覧を出す。今は知らせるだけで、7 章の直しが済んだら失敗にする。
  手数・操作から表示までの時間・フレーム時間・指の届く範囲の検査は案のまま (UI_PRINCIPLES.md の 8 章)。
- **しなかったこと**: 下に常に出るタブ (行き先が少なく、Telegram 2026 の反発の条件に当たる)。今回は画面を変えていない (案だけ)。
- **確かめたこと**: `TouchTargetCheckTest` で、隣と接している 40dp・44dp の押せる要素を見つけ、周りが空いた 32dp と IconButton は見つけないこと。
  `TouchHitBehaviorTest` で、見た目の外を押したときにどの要素が反応するか (上の当たり判定の動き)。`TouchTargetCheckTest.agreesWithHitBehavior` で、検査の判定がその動きと合うこと。
  最初の live-test で、リアクションの枠 (高さ 28dp)・続けて送ったメッセージの行 (高さ 24〜44dp)・絵文字を選ぶ画面の枠 (44dp) が見つかった (UI_PRINCIPLES.md の C-4・C-6・C-7)。
  ATF が Robolectric で Compose の中身を見ないこと (試験用のテストで確かめ、結果だけ残してテストは消した)。
- **確かめていないこと**: 原則に沿って作り直した画面が実際に速く・使いやすくなるか。エミュレータで ATF が働くか。
  レビューの分類の正しさ (1 人で分類し、標本は 160 件)。要約で読んだ出典の原文。

## D-046 見た目の作り直しより、体験 (UX) を先にする

- **判断 (持ち主との相談、2026-11-13)**: docs/UI_PRINCIPLES.md (D-045) の原則のうち、体験に関わるもの
  (P-1 待たせない・P-2 つながっていなくても読める・書ける・P-3 よく使う操作は 2 手以内・P-6 配置を変えたら手数と時間で比べる) を先に進める。
  見た目の作り直し (UI_PRINCIPLES.md 7 章のホームの配置など) は、その後にする。
- **順番**:
  1. よく使う作業 (読む・返す・自分宛てを拾う・切り替える・探す) を、始まりと終わりの状態で決める (UI_PRINCIPLES.md 9 章)
  2. e2e (D-018) でその作業をし、手数 (押した回数) と時間 (最後の操作から終わりの状態が出るまで) をログに出す。今の値を基準として残す
  3. 見た目を変えずに直せる体験の問題を直し、2 の数値で比べる (例: C-2 再接続で履歴を捨てる、C-5 未読の始まりへ戻れない、P-2)
  4. 見た目の作り直しは、2 の測定を入れた後に、数値が悪くならないことを確かめながら進める
- **理由**:
  - UI_PRINCIPLES.md 4 章のレビューの分類では、低評価の多くは「使えない」(つながらない・落ちる・取れない) で、配置への不満は少なかった
    (Telegram 100 件中「操作・配置」1 件、WhatsApp 60 件中 3 件)。
  - Discord の 2023 年の刷新への反発の中身は、配置そのものより、遅さとよく使う操作が遠くなったこと (UI_PRINCIPLES.md 3 章。要約で読んだ)。
  - 見た目を先に変えると、比べる基準 (手数・時間) が無いまま変わり、悪くなっても気づけない (P-6)。
- **測り方の決めごと**:
  - 手数は、利用者がする操作 (押す・長押し・すべらせる・戻る) の回数。文字の入力は数えない (入力欄を押すのは数える)。
  - 時間はエミュレータ (CI) の値なので、絶対値ではなく、前の実行・直す前との比較だけに使う。
    `UiDevice.wait` は問い合わせの間隔が粗いので、30ms ごとに自分で探して測る。`findObject` は既定で画面が 500ms 落ち着くのを待つので、
    測る間だけ待たない設定 (`Configurator.waitForIdleTimeout = 0`) にする (レビューの指摘)。
  - 測るのは、配布版 (R8 適用後) を外から操作する e2e の `uxTasks`。CI のログの「よく使う作業の手数と時間 (ux)」にまとめて出る。
  - 速い回線 (端末の localhost を `adb reverse` でランナーのサーバーへ) と、遅い回線の 2 回測る。遅い回線は、
    ランナーの上に置いた遅延の中継 (`.github/scripts/latency-proxy.py`、片道 150ms・帯域は絞らない) を通す (#57)。
    速い回線だけでは、どの切り替えも 0.2 秒前後で、キャッシュをすぐ出す直し (C-2 など) の効果が数値に出なかったため (#55 の基準)。
    エミュレータの `adb emu network delay` は、往復が 5 回とも約 500ms の実行と、途中から 13〜41ms に戻る実行があり、当てにならなかった。
    遅延が効いていることは、毎回、端末からの往復時間 (`round_trip`) で確かめる。
  - つなぎ直した後の切り替えは、アプリの再同期が終わった (開いているチャンネルの取り直しまで済んだ後に出るログ `GiracleSync` の `resync:`) のを待ってから測る。
    待たずに測ると、再同期の前の状態を測っていた (#57 で記録を足して分かった)。
  - 当面は知らせるだけで、数値で失敗にしない (エミュレータの時間は揺れるため)。手数は決まった値なので、作り直しが始まったら上限を決めて失敗にする。
- **代替案**: 見た目 (7 章) から作り直す。比べる基準が無いまま変わるので採らなかった。
- **確かめていないこと**: 測った作業が、利用者が実際によくする作業と合っているか (頻度のデータは無い。UI_PRINCIPLES.md 1 章の出典からの判断)。

## D-047 つなぎ直した後も、開いていないチャンネルの履歴を残す (C-2)

- **見つけたこと**: WebSocket をつなぎ直すたび (背面から戻ったときなど)、`ChatStore.resync` が開いていないチャンネルの履歴を捨てていた。
  次に開くと、中央の回転アイコンで取り直しを待たされた (docs/UI_PRINCIPLES.md の C-2。P-1 待たせない に反する)。
- **判断**: 最新側に揃っている履歴は、最新 60 件 (チャンネルを離れたときに残す件数と同じ) を「キャッシュから」(`fromCache`) の印を付けて残す。
  開いたらすぐ出し、裏で取り直して差し替える (起動時のスナップショットの復元と同じ扱い)。古い側を読んでいた途中の履歴は、続きを読む位置が分からなくなるので、今までどおり捨てる。
- **しなかったこと**: つなぎ直したときに、すべてのチャンネルを裏で取り直す (チャンネルの数だけ問い合わせが増える)。
- **確かめたこと**: `ChatStoreOfflineTest.resyncKeepsOtherChannelsAsCache` で、つなぎ直した後も履歴が残り、件数が抑えられ、取り直しの印が付くこと。
  `cacheIsNotExtendedNorMarkedRead` で、キャッシュに新着を足さず、既読にもしないこと。
  e2e (D-046) の遅い回線 (往復約 300ms) で、つなぎ直した後に B を開く時間 (switch_after_reconnect) が
  API 35 で 433ms → 116ms、API 37 で 449ms → 138ms になり、2 回目に開く時間 (switch_again、185〜221ms) と同じ水準になった
  (#57 の基準と #59 の CI。ログの `kept=1` で B を残したことも確かめた)。
- **確かめていないこと**: 取り直した後の位置合わせが、つなぎ直した後の未読のあるチャンネルで未読の始まりに合うこと (e2e の B は未読の位置合わせが要らない状態)。
- **キャッシュの扱い (レビューで見つけたもの。起動時の復元にも前からあった)**:
  - キャッシュには WebSocket の新着を足さない。足すと、切れていた間の投稿が抜けたまま新着だけが続いて見える。
  - キャッシュを見ている間は既読にしない。最新の新着で既読にすると、見ていない投稿までサーバー上で既読になる。
  - キャッシュの続き (古い側・新しい側) は読まない。取り直しで別の範囲に差し替わり、つなぐと抜けができる。ロックを待つ間に差し替わったときも読まない。
  - 未読の始まりへの位置合わせは、取り直した後にする (キャッシュには切れていた間の投稿が無く、未読の始まりが分からない)。
    キャッシュを見ている間に利用者がスクロールしていたら、その位置を優先する。
  - キャッシュを出しているときに取り直しに失敗したら、トーストで知らせる (画面の中央の案内は、何も出せないときだけ)。
- **制限**: 開いてから取り直しが済むまでは、切れていた間の投稿が抜けた古い表示になる。取り直しに失敗すると、その表示のまま残る (トーストで知らせる)。

## D-049 未読の始まりへ戻るボタン (C-5)

(D-048 は別のセッションの Test Lab の作業 (#56) が使う)

- **見つけたこと**: チャンネルを開いたときは未読の始まりに合わせてあるが、上 (古い側) へ読み進めた後に戻る手段が無かった。
  「最新へ」は未読の始まりを通り越して一番下へ行く (docs/UI_PRINCIPLES.md の C-5)。
- **判断**: 「最新へ」の上に「未読の始まりへ」のボタンを出す。押すと、開いたときと同じ位置 (未読の始まりの少し下まで見える) へ移る。出す条件は次のどちらか。
  - 未読の始まりが画面の下に隠れたとき (上へ読み進めた後)
  - 未読の始まりが画面の外にあり、開いてからまだ一度も画面に出ていないとき (通知から別のメッセージへ飛んだときなど)
  一度見て下へ読み進めた後 (未読の始まりが上に隠れたとき) は出さない。普通に読み進めるたびに出ると邪魔になるため。
  未読の始まりは、開いた時点の既読時刻 (`readTimesBefore`) で決める。自分が送信するとその時刻が進むので、ボタンは消える。
  既読側のメッセージを 1 件も読み込んでいないとき (通知から飛んだ後・「最新へ」の後など) と、キャッシュを出しているとき (D-047) は、
  未読の始まりが分からないので出さない (レビューの指摘。読み込んだ中でいちばん古いものへ飛ばしてしまうため)。
- **参考**: Element X は「最新へ」と「未読の始まりへ」を別のボタンで持つ (UI_PRINCIPLES.md 3 章)。
- **確かめたこと**: e2e の `back_to_unread` で、未読の始まりを上へ隠した後、ボタン 1 手で未読の始まりが見えること (API 35 で 90〜93ms。#60)。

## D-050 1 セッションで扱う PR は 1 つまでにする

- **判断 (持ち主との相談、2026-11-13)**: 1 つのセッションで扱う PR は 1 つまで。PR をマージしたら、そのセッションの作業は終える。
  CLAUDE.md の「一つの作業が終わっても、報告で止めない。次に価値のある作業を自分で探して続ける」は残し、
  続け方を「同じセッションで次の作業に入る」から「次の作業を docs/ROADMAP.md に書き、新しいセッションに渡す」に変える。
  渡し方は、そのとき使える手段 (タスクの提案カード、新しいセッションの作成など) から選ぶ。
  ROADMAP には候補を書き、順番は書かない。どれをやるかは受け取ったセッションが選ぶ (渡す側が決めると、受け取った側が外を調べて選び直す余地が減るため)。
  リリースを出すときは、これまでどおり案内 (releases/notes/) と版の更新を機能の PR に含め (#35〜#52 と同じ)、マージ後に release ワークフローを手動で実行する。PR を増やさない。
- **理由**:
  - 1 つのセッションが #55 → #57 → C-2 (#59) と PR を重ね、1 回の応答ごとに約 47 万トークンの経緯を読み直していた。
    使用量は、ほぼセッションの長さの 2 乗で増える (応答の回数 × 毎回読み直す量)。
  - その結果、使用量の 5 時間上限に達し、Test Lab のセッション (#56) が約 1 時間 40 分止まった。上限は持ち主のほかの作業も止める。
  - 長いセッションは、前の経緯を読み違える機会も増える。
  - 引き継ぎに必要なことは、ROADMAP・DECISIONS・RESEARCH に書く運用がもうある。
- **考えたが本質ではないとしたもの**:
  - 手元でビルドできない (Maven Central の 429): 相談の時点 (21:50 JST) には Maven Central も Google のリポジトリも 200 を返した。
    一時的な制限とみられ、対策は 429 がまた続いたときに考える。
  - 判断の番号のぶつかり (D-046 の重複): 並行するセッションの症状。1 セッション 1 PR で起きにくくなるので、続くなら考える。
- **確かめていないこと**: 新しいセッションでの読み直し (CLAUDE.md・ROADMAP など) の分を含めて、使用量がどれだけ減るか。
